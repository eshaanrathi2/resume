Time, Clocks, and the Ordering of Events in a Distributed System

Leslie Lamport, 1978. Paper

This is one of those papers everyone in distributed systems cites, and for good reason. Lamport's point is simple and a bit unsettling: in a distributed system, "what happened first" is not a physical fact you can always observe. It is a relation you have to define.

The problem

Processes do not share memory. They only learn about each other through messages. There is no global clock sitting in the middle of the network telling everyone the "real" time. So if process A writes a value and process B reads something later, you cannot always say which event came first by looking at wall clocks. Clocks drift. Messages take time. Relativity even gets a cameo in the intro, which I did not expect in a systems paper.

If you cannot order events, you also cannot reason cleanly about causality: did this update happen before that read? Did two writes commute, or did one overwrite the other? That question shows up everywhere in replication.

Happened-before

Lamport defines a relation happened-before, written a → b. It is the smallest relation that satisfies:

  1. If a and b are in the same process and a comes before b in that process's local order, then a → b.
  2. If a is the send of a message and b is the receive of that same message, then a → b.
  3. If a → b and b → c, then a → c. Transitivity.

If neither a → b nor b → a, the events are concurrent. Not "at the same time" in a physics sense. Just: neither could have influenced the other. That distinction is the whole paper, really.

Logical clocks

A logical clock is a counter C on each process. Rules:

  1. Before each local event, tick: C := C + 1.
  2. On send, attach the current C to the message.
  3. On receive, set C := max(local C, timestamp in the message) + 1.

This gives the Clock Condition: if a → b, then C(a) < C(b). The converse is not true. Equal or inverted timestamps do not prove concurrency; they only fail to prove causality. Still, this is enough to assign numbers that respect happened-before.

Total order

Logical clocks give a partial order. To get a total order, break ties with process ids: if timestamps are equal, the lower pid wins (or whatever deterministic rule you pick). Now every event has a unique place in a global sequence.

Lamport uses this to implement distributed mutual exclusion without a central coordinator. Each process timestamps a request, broadcasts it, and enters the critical section when its request is the earliest in the total order and it has heard from everyone else. The algorithm is not what most systems ship today, but the idea stuck: agree on an order, then execute as if that order were the history of the world.

Physical clocks

The last section is about real clocks. If you want timestamps to match physical time, clocks must not run too fast or too slow, and they must be synchronized closely enough relative to message delay. Lamport gives bounds: how much drift you can tolerate, and how often you need to correct.

This is the ancestor of a lot of later work on clock synchronization, TrueTime-style APIs, and "commit wait." Logical time tells you causality. Physical time is what you reach for when you also care about external consistency, or about events that never exchanged a message.

What I took from it

  • Causality is a graph of sends, receives, and local order, not a property of wall-clock readings.
  • Concurrent does not mean simultaneous. It means "no information flow."
  • Once you have a total order of events, many coordination problems collapse into "apply operations in that order."
  • Replication and storage are full of this: write pipelines, log ordering, failover, and "which replica is ahead" are happened-before problems wearing production clothes.

Short paper. Large shadow. I keep coming back to it when a system starts arguing about whose version of the data is newer.
